# map-calls

Deliver an editable file that opens in draw.io. By default, use one page to show the in-repository functions reachable from the specified entry point. Give each function one node. Arrows follow actual calls or control flow confirmed in the source.

## Wait for required answers

If the developer needs to provide information, make a choice, or grant approval, do only the work needed to formulate the question. Ask it as the last action of the turn, then pause the task, including read-only searches, call tracing, directory creation, and file writes. An asynchronous prompt confirms delivery. Wait for the developer's actual response before resuming.

At the start of the next turn, check whether the developer resolved every pending item. Use a default or alternative once the developer explicitly accepts or provides it. Keep waiting if the prompt times out, receives no answer, or only has a preselected value. If an answer is partial or ambiguous, or if the developer rejects the default output path without supplying another one, ask only for the missing information and end the turn. Begin tracing once the entry point and output path are clear.

## Identify the entry point and output path

- When invoked without arguments, ask for a repository path, module directory, or entry-point function. A path or function name alone is sufficient to start.
- For a function name, find its definition in the current repository. Distinguish namespaces, overloads, template specializations, and build targets. For a module or repository path, use exported APIs, registration sites, and actual call sites to identify the entry point. If there is a single reasonable entry point, use it. Otherwise, ask the developer to choose from candidates listed with their full signatures, relative paths, and short descriptions.
- A module path limits the entry-point search. Use the version-control root as the tracing boundary and follow calls across modules in that repository. For a project without version-control metadata, use the supplied repository root. Ask for the root if the developer supplied only a module path and the root cannot be determined.
- If the developer has not specified an output path, ask at startup whether to use the default directory under the repository root at `<project>/codex/reports/`. Show the absolute path and accept a custom directory or a full `.drawio` file path. Combine this question with entry-point selection when both are needed.
- Use a supplied output path directly. Resolve relative paths from the repository root.
- Optional settings include maximum tracing depth, initial expansion depth, and branches to collapse by function or module. The entry point is at depth zero and each call adds one level. By default, trace all reachable in-repository levels and show through depth two initially. An explicit collapse setting takes precedence for that branch's initial visibility. Match module selections against repository-relative directories and collapse the branch roots where calls enter the module.

## Trace calls from the source

1. Read the entry-point definition and the source files used by the active build. Verify each call expression and its actual target definition. Use existing symbol indexes, compilation databases, and language tools when helpful. A declaration, a commented-out implementation, a function address, or a registration entry alone does not establish a call.
2. Traverse in order of shortest call distance. Identify each function by its definition location and full signature. Analyze each target once and retain every incoming call edge and call site. Keep recursive and mutually recursive edges. For calls repeated by a loop, add that detail to the edge tooltip as needed. Stop at the configured depth and label the boundary tooltip to distinguish the depth limit from an in-repository leaf. By default, trace to the lowest implementation in the repository and stop at standard-library, system-library, or external code. Treat external headers and library implementations as boundaries.
3. For function pointers, virtual calls, template dispatch, and registries, connect the call site to the assignment or construction, registration, selection condition, and target definition. Draw an edge for each evidenced target and record the condition that selects it. When the target set may be incomplete, add a dashed branch with a localized label indicating an unresolved target. If only the call expression is known, use it as the endpoint and mark the dashed edge as unresolved. Record the call site and explain why the target could not be determined.
4. For each function, record its display name, full signature, parameter types and meanings, purpose, repository-relative path, and definition line number. Use declaration comments and the implementation to establish parameter meanings. State the basis of any inference and flag meanings you could not confirm. Record definition locations for inline functions and template kernels too.

## Generate the draw.io file

Match the language of the user's diagram request. Use Chinese for a Chinese request and English for an English request. Follow an explicitly requested diagram language when provided. Infer the language from the request's natural-language wording. If a follow-up supplies only a function name or path, keep the language of the original request.

Use the chosen language consistently for all generated text, including page names, titles, branch and edge labels, legends, navigation labels, and tooltip headings and explanations. Preserve function names, signatures, parameter names, source paths, condition expressions, and language keywords as written in the source.

Use the [editable sample](assets/shared-kernel.drawio) for formatting, decision diamonds, independent folding, fixed ports, and shared-target routing. Adapt the sample's labels to the chosen language. Take locations and conditions for each actual diagram from the source being analyzed. Write uncompressed `mxfile`, `diagram`, `mxGraphModel`, and `root` XML. Use an XML library to escape signatures, template syntax, and line breaks.

- **Function nodes** use an `object` wrapper with `id`, `label`, and `tooltip` around a vertex. Use only the function name as the label. Enable `tooltips="1"` and `fold="1"` on each page. Attach the tooltip to the function container so it remains available while collapsed.
- **Function tooltips** use plain text on multiple lines. Start with the full declaration, including types and available default values. Follow it with localized sections for purpose, parameters, and source, separated by blank lines. List parameters in declaration order, one per line, using a hyphen, the parameter name, the language's colon style, and its meaning. For an unnamed parameter, identify its position and type and state its role. If there are no parameters, say so in the parameter section. When template parameters need an explanation, list them one per line in a separate section between parameters and source. End with the repository-relative path and definition line.
- **Decision nodes** use native diamonds (`shape=rhombus`) for decisions that change the call path. Label the node with the actual condition and name the enclosing function and source line in its tooltip. Label outgoing edges with localized yes and no labels, the actual enum values, or `default`. Route each edge to its corresponding next step. Keep function nodes tied to real definitions and make the call expressions traceable through the control flow.
- **Branch roots** use native collapsible containers, for example `swimlane;collapsible=1;`. Put descendants exclusive to a branch inside its container and position them relative to it. Keep incoming edges outside the container and internal call edges inside it. Store expanded and collapsed sizes in `mxGeometry` and `alternateBounds`. For a branch that starts collapsed, set `collapsed="1"`, use the collapsed size as the current geometry, and reserve room for the expanded size. Prefer fixed external ports on the visible container header so their anchors stay stable when folding. Specify internal waypoints in the container's coordinate system.
- **Shared functions** appear once. Point all incoming call edges at that node. Place it in the closest common container of its callers or at page level. Put edges that cross container boundaries at a level that includes both endpoints. Use directed edges for actual calls and container nesting for folding. Folding one caller's branch should leave the shared target visible to its other callers. If a deep shared node needs to start hidden, use a separate collapsible area under the common ancestor. Check initial visibility against shortest call distance.
- **Back edges** point to the existing target node. Use a bent route with a dashed stroke or a localized recursion label. Document dispatch evidence and conditions in confirmed indirect-edge tooltips and visibly mark unresolved edges.
- **Colors and shapes** use light purple fill `#E1D5E7` and purple border `#9673A6` for key decision diamonds on the main path. Use the default white fill and border for other diamonds and ordinary rectangular nodes. Use the default palette for collapsible containers. Use the same purple fill and border for explanatory boxes such as layout parameters, address calculations, and the legend.
- **Typography** uses `fontSize=18` and `fontStyle=1` for the main title, section headings, flow nodes, decision nodes, and edge labels. Use the default text color. Set English text in Times New Roman and Chinese text in the default draw.io font. For mixed labels, `fontFamily=Times New Roman,Helvetica,Arial,sans-serif` lets Chinese characters use a fallback font. Use the default font and regular weight (`fontStyle=0`) for both languages in explanatory boxes, with size 15 as the reference for body text.
- **Canvas and routing** lay out the main path first. Reserve separate lanes for branches, merges, and back edges. Size the canvas for all branches expanded, with room for nodes, labels, and bends. Keep the main path oriented consistently and prefer short straight or orthogonal edges. If automatic routing overlaps other edges, crosses unrelated nodes, or obscures labels, use separate ports and explicit waypoints with `Array as="points"` in `mxGeometry`. Set `noEdgeStyle=1` when the waypoints must be followed exactly. Use distinct incoming ports for shared targets and order fan-in and fan-out ports to match the nodes. Use line jumps (`jumpStyle=arc`) for unavoidable crossings to show that the lines are separate.
- **Pagination** is reserved for large branches that still crowd the main path after expanding the canvas and can be split at a few boundaries. Keep the unique entry node and its call edges on the main page. Add `link="data:page/id,<page-id>"` to the entry `object` to open the detail page. Add a link back to the main page on the detail page. Use linked navigation markers for cross-page calls. Point each marker to the page containing the unique definition and record the caller, target, and call site in its tooltip. Keep drawn edges within a page.
- When the output path is a directory, create it as needed and name the file `<entry-point>.calls.drawio`. Use the supplied filename for a full output path. Preserve existing hand-edited drawings.

## Verify the deliverable

- Parse the actual output XML and check page IDs, parent-child relationships, edge endpoints, and page links. Compare edge directions, the incoming edges of shared functions, and the conditions and targets of each decision branch against the source.
- Check that generated diagram text uses the chosen language. Spot-check tooltips for the declaration, section order, and one parameter per line. Check node fill and font size.
- Check the initial state, the fully expanded state, and each branch collapsed independently. Look for overlapping lines, routes crossing unrelated nodes, and obscured labels. Confirm that the entry point, external incoming edges, tooltips, and sibling branches remain accessible when collapsed. Confirm that each branch's exclusive descendants and edges appear when expanded.
- If a draw.io editor is available, open the file and test folding, tooltips, page navigation, and label visibility. State when verification was limited to structure.
- Identify any limits due to build variants, template conditions, depth cutoff, or unresolved indirect dispatch. Deliver a clickable link to the file.
